Yes, This Section Must Be Added

The current design document mentions the market data node as a separate component, but it lacks a critical section: how the matching engine disseminates market data to the algo under test. This is the core of the entire simulation loop — the algo needs to see market state in order to make decisions.

Why This Section Is Critical

1. The algo depends on market data for decisions: Your algo needs to see order book snapshots, last traded price, IEP/IEV, session status, etc., before it can decide whether to place, modify, or cancel orders.
2. Market data latency and granularity directly affect simulation realism: If the algo sees "perfect, instantaneous" market data, it will perform better than in reality. You need to model dissemination latency, data granularity (tick-by-tick vs. aggregated), and the market state at the time the data arrives.
3. Matching and dissemination are separate concerns: The matching engine produces events; the market data node decides "when" and "in what form" to disseminate those events to the algo. Separating the two allows independent configuration.

Suggested Section Content

Section: Market Data Dissemination

11.1 Dissemination Model

· Push mode: Algo subscribes to specific securities; market data node pushes updates when events occur
· Pull mode: Algo actively queries the latest state before making decisions
· Hybrid mode: Push notifications + on-demand snapshots

11.2 Dissemination Granularity

· Tick-by-tick: Every order book change is pushed; most realistic but high data volume
· Conflated: Aggregated at fixed intervals (e.g., 10ms), simulating HKEX's SS/SP feed behavior
· Hybrid: Conflated during continuous trading, IEP update push during auctions

11.3 Dissemination Latency

· Processing latency: From matching event generation to market data node processing
· Network latency: From market data node to algo
· Algo processing latency: Time from algo receiving data to making a decision

11.4 Data Content

· Order book snapshot (top N levels)
· Last traded price and volume
· IEP/IEV (during auctions)
· Session status changes
· VCM state
· Order confirmation/rejection/fill reports

11.5 Algo Interface

```java
public interface MarketDataListener {
    void onBookUpdate(BookSnapshot snapshot);
    void onTrade(TradeEvent trade);
    void onIepUpdate(IepUpdate iep);
    void onSessionChange(SessionPhase phase);
    void onVcmUpdate(VcmState vcm);
}
```

11.6 Coupling with the Matching Engine

· The matching engine produces events synchronously (within the matching loop)
· The market data node consumes events asynchronously (on a separate thread)
· Orders generated by the algo after receiving market data return to the matching engine asynchronously
· This introduces round-trip latency, which must be modeled

Key Design Decisions

Decision Options Recommendation
Push vs. pull Push-primary, pull-supplementary Push (more realistic)
Granularity Tick-by-tick vs. conflated Conflated (simulates HKEX)
Latency Fixed vs. random vs. market-based Configurable (support all three)
Ordering guarantee Global ordering vs. per-security ordering Per-security (better performance)

Why This Section Cannot Be Omitted

Without this section, implementers will default to the algo directly accessing the matching engine's internal state — which is unrealistic and would cause:

· The algo sees instantaneous market state, whereas in reality it has latency
· The algo is not constrained by data granularity, whereas in reality it only sees conflated snapshots
· The algo's orders arrive instantly, whereas in reality it takes time

These differences make backtest results systematically optimistic. This section is key to ensuring simulation realism.
